# Phase 8 — Windows installation ISO preflight and virtual CD-ROM staging (experimental)

## Implemented, verified scope

`bootnexa-media inspect-windows-iso <ISO>` reads a **local regular file** and emits a metadata-only JSON envelope. It walks the primary ISO9660 tree with bounded depth (8), directory sizes (1 MiB), entry count (4096), path/extent validation and strict rejection of multi-extent, interleaved, Rock Ridge/SUSP, duplicate, overlapping or ambiguous directory records. Large WIM file extents can be examined **without** widening the previous small EFI extraction caps. The two APIs remain independently gated.

The Windows-specific classifier reads at most a WIM/ESD header per named file: `SOURCES/BOOT.WIM` plus either `SOURCES/INSTALL.WIM` or `SOURCES/INSTALL.ESD`. It checks MSWIM magic, a limited supported format version, header bounds, image-count sanity and rejects spanned archives. It verifies the x64 PE/COFF EFI subsystem header of `EFI/BOOT/BOOTX64.EFI`, presence of `SETUP.EXE` and an El Torito UEFI catalog, and observes UDF Volume Recognition Sequence signatures. **The metadata-only Windows Setup candidate check is not authentication, format-complete WIM parsing, Windows version identification, installer installation or guest boot evidence.** Synthetic fixtures can pass it by design.

`bootnexa-media stage-windows-virtual-cdrom <ISO> <existing-real-directory>` requires the candidate gates to pass and refuses UDF-recognised images until a separately reviewed UDF parser exists. It copies the entire source ISO in bounded 64 KiB chunks into a **new randomly named regular `.iso` file**, synchronizes output, independently hashes the source before/after copying and verifies the staged file by full SHA-256 read-back. It refuses symlink output directories, does not overwrite an existing output, and removes newly created partial outputs after failures. The output is a **virtual optical-disc image** and is NOT a GPT/FAT32 USB disk or a Windows installer. It can only be attached as an optical image to a VM in future tests.

The browser's local ISO library now shows Windows primary-directory payload type/bytes and a UDF recognition warning, while refusing any physical disk writer or Windows OS boot claim.

## Verified tests

- Synthetic MIT/open-source-only ISO9660 with x64 EFI-formatted stub, `SETUP.EXE` placeholder and fabricated WIM headers; no Microsoft binary or Windows image is shipped.
- Header corruption, spanned/zero-image WIM, tampered x64 EFI, incomplete Windows layout, UDF recognition (fail-closed staging), and symlink destination denial.
- Regular-file optical-image copy with three SHA-256 checks and unchanged source; 64 MiB sparse WIM extent is inspected without relaxing small virtual EFI extraction limits.
- Rust unit tests, browser Playwright UDF/Windows limitations, GitHub's Linux native preflight CI.
- **No real Microsoft Windows Setup boot has been attempted or proved in this test corpus.** A successful synthetic UEFI boot elsewhere in the repository is NOT a Windows Setup boot.

## Phase 8 continuation — bounded ECMA-167 structure and FAT32 decision model

The new `inspect-udf-structure <ISO>` command validates the UDF 2048-byte sector anchor (at LBA 256), descriptor tags including checksum and descriptor CRC, bounded Main Volume Descriptor Sequence, a single type-1 partition map, a matching partition descriptor, and the File Set Descriptor and root File Entry ICB. It rejects invalid extents, altered checksums/CRCs, unsupported partition types, multiple or ambiguous layouts, unsupported root file forms, and truncation. It does **not** read UDF filenames, recurse directories, extract any file, or verify Windows Setup boot. A matching UDF recognition sequence plus a valid descriptor chain does not authorize virtual CD-ROM staging or an installer. Only synthetic structural fixtures have been tested.

The `plan-windows-media <ISO>` command returns a read-only feasibility plan alongside the existing Windows preflight report: GPT/UEFI/FAT32 are **proposed** (not created), FAT32's 4,294,967,295-byte single-file ceiling is enforced in arithmetic, and a larger `install.wim` is flagged as requiring **a separately implemented and validated split-WIM encoder**. The planner suggests a 3,800 MiB target segment but never creates `.swm` data or estimates exact SWM part count. Solid ESD outer headers are recognized but their compressed resources and edition/version indexes remain unverified. Unknown and ambiguous layouts remain non-actionable, and every plan records `physicalWriteAuthorized: false`, `virtualUsbBuilderImplemented: false` and `windowsSetupBootVerified: false`.

Dedicated Rust and synthetic Python CI tests verify valid/invalid UDF descriptor chains, independent source parsing, mutated tags/CRC/root, no staging, precise FAT32 boundary values, ESD header vs resource qualification and that the old bounded EFI extraction pathway was not widened. These are **preflight-only** proofs, not actual Microsoft-media test coverage.

## Phase 8 continuation — restricted UDF filename tree (metadata only)

A further staged change introduces `inspect-udf-tree <ISO>`, a bounded read-only File Identifier Descriptor reader for a **restricted single-partition UDF profile**. It checks UDF FID tag checksum/CRC, partition reference, file-entry type, ICB logical location, allocation descriptor lengths and nonoverlapping file extents. It enforces directory depth, path-count and directory-byte limits, refuses symlink-like/unsupported file types, deleted FIDs, ambiguous aliases, unsupported allocation modes, unsafe names and unqualified encodings. Only ASCII names carried in OSTA 8-bit or 16-bit compressed Unicode are accepted; non-ASCII localized file names are explicitly unsupported until a separate Unicode normalization review. File contents are never opened as named streams, copied, decompressed or exported.

The independently parsed UDF path/length inventory is compared to the ISO9660 primary directory list when both exist. A mismatch is recorded as `udf_iso9660_namespace_conflict` and **neither match nor mismatch grants installer or device-write authority**. The existing `udfTranslationSupported` field stays `false` because safe UDF *content extraction* and Windows Setup compatibility have not been established. A synthetic Windows-shaped UDF tree can report `windowsSetupFilenameCandidate: true`, but this identifies only path names, not genuine Microsoft files. All media plans remain `actionable: false`.

The parser has synthetic adversarial tests for malformed FID CRC, invalid logical block, duplicated ICB, modified directory/file extents, filename conflicts, and nonqualifying compressed Unicode. These tests do not demonstrate compatibility with current Microsoft Windows installation media.

## Phase 8 continuation — bounded UDF content streaming into virtual GPT/FAT32 (synthetic only)

The developer-only `bootnexa-media build-udf-small-virtual <restricted-UDF-ISO> <existing-real-directory>` builds a **96 MiB anonymous in-memory-name-free regular-file disk**, with a verified GPT partition table and FAT32 filesystem. It is a restricted *media construction test*, not a Microsoft Windows installer. It never opens a real block device, disk handle, physical USB target or existing output file. Output names are randomly generated, the output directory must exist and must not be a symlink, and any failed final export removes its new partial output. Source inputs above 256 MiB are refused outright; payloads exceed neither 32 MiB per file nor 48 MiB aggregate.

The reader now validates the complete supported UDF file tree, rejects aliases/overlapping extents/unsupported names, revalidates each file's descriptor chain before opening its bounded source stream, and copies in 64 KiB chunks across disjoint UDF extents. Per-file source SHA-256 hashes are computed **before and after** the copy and compared to independent FAT32 file read-back SHA-256 hashes. GPT headers and partition table are reverified. A full 96 MiB image SHA-256 is computed and independently compared after exporting to a new regular `.img`. A structurally formatted x64 EFI PE header is checked as a *file-format gate*, not as proof of executable validity, trust or bootability.

New adversarial tests exercise fragmented two-extent source files, CRC-valid overlapping extents, symlink destinations, input capacity rejection and no-output-on-invalid-input behavior. Synthetic Windows-like filenames in the test fixture contain **no Microsoft binaries** and do not make the output a Windows Setup installer. The CLI report explicitly records `virtualOnly=true`, `physicalWriteAuthorized=false`, `installerCompatible=false`, `windowsSetupBootVerified=false`.

The outer WIM/ESD header parser also bounds its lookup-table, XML, boot-metadata and integrity-table resource ranges, requiring in-file offsets and non-overlapping physical ranges. This **does not** decompress resources, check their cryptographic hashes, validate WIM edition/image metadata, or create valid split `.swm` files. The older Windows preflight and media feasibility planner still report Windows boot and large-install-payload support as unqualified.

## Latest Phase 8 increment — wimlib SWM artifact qualification

The developer-only `split-wim-virtual` command invokes a trusted installed wimlib verifier against a regular WIM file, produces new `install*.swm` files and re-verifies the full split archive. Independent checks enforce actual per-part FAT32 file limits and SHA-256 read-back; failures do not leave partial artifact directories on normal controlled paths. This does **not** generate a real Windows bootable disk or establish Windows Setup bootability. See [WIM/SWM proof and remaining guest-boot gates](WINDOWS-SWM-SETUP-QUALIFICATION.md).

## Remaining to complete Phase 8

1. Expand the restricted read-only UDF FID tree parser beyond ASCII and short/long allocation extents: normalize non-ASCII compressed Unicode, handle separately-qualified Extended File Entries, robust UDF 1.02/2.01 cases, and fuzz against real UDF images. Restricted small-file UDF source streaming and virtual FAT32 read-back now exist, but full UDF compatibility and real Microsoft Windows Setup boot, plus independent WIM/ESD resource integrity, remain unqualified.
2. Verify actual `boot.wim` and `install.wim`/`install.esd` using a qualified WIM/ESD decoder (including compression methods, WIM resource integrity, image indexes, version and edition, encrypted ESD and multi-part cases). This phase only validates the fixed-size outer header.
3. Design the actual FAT32+NTFS Windows Setup virtual **USB disk** layout and a safe verified split-WIM (`install.swm`) or other proven UEFI strategy for files larger than FAT32's 4 GiB minus 1 byte maximum. Do not blindly copy oversized files to FAT32.
4. Obtain Windows ISO through [Microsoft's official download page](https://www.microsoft.com/en-au/software-download/windows11), verify its publisher-published SHA-256 for its language and version, then test Windows Setup launch in QEMU/OVMF using a read-only virtual ISO, with guest evidence and independent post-run checks. Do not download, bundle, commit or redistribute Microsoft images from BootNexa CI without appropriate licence and provenance.
5. Add per-image Secure Boot / legacy BIOS and Windows 11 hardware requirements matrix and human-operated sacrificial physical-media acceptance *only after* separate privileged helper, protected-device identity and production signing gates.

**Physical USB writing, target-drive selection, formatting, Windows Setup customization and installer provisioning remain disabled.** Virtual demonstration outputs are newly created regular files only; writes to raw devices and existing files are not implemented. No disk-device handle is opened for writing.
